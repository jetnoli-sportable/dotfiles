System map

Two data planes hold the whole thing together: the attention plane — a pane-local tmux option acting as a message bus — and the content plane — Claude's session transcripts on disk, read and written by the nvim bridge.

The signal contract — @claude_blocked

ValueMeaningSet byRank
unsetnothing pendingpane-focus-in hook · start hookglyph/scan fallback
needs-inputagent blocked on you (permission, question)Notification hook0 — ✳ needs you
nvim-bufferagent blocked on a buffer you're editingdecision-buffer / parked-items skills0 — treated as needs-input
doneturn ≥ 30 s finishedStop hook1 — ✔ finished

Any non-empty, non-done value ranks 0 — the value space is open for future producers (e.g. a task driver marking "review ready"). This bus is the natural integration point for anything new we build.

Gaps & drift found in this audit

in progress Hooks never wired → one paste left

~/.claude/settings.json had no hooks block — the v1 build plan's "one manual step left" never happened, leaving the push pipeline dormant on the version-pinned content-scan fallback. 2026-07-06: the hook script was live-verified (needs-input sets the marker, start clears it) and the exact block prepared at logs/claude-hooks-block.json; the harness blocks agents from editing their own hook config, so wiring it is a single user-run merge command.

run the printed merge command, restart/reload hooks, then fold settings.json into the stow-claude-config task so it's reproducible.

fixed 2026-07-06 parked-items wait-channel latch

parked-items blocked on a fixed channel name parked-review-done — the stale-signal latching footgun decision-buffer's own skill warns about. A crashed review could make the next one return instantly.

done — the skill now mints a unique parked-review-done-$$-$RANDOM channel per invocation, same as decision-buffer.

high Newest-JSONL heuristic

The nvim bridge picks the newest-mtime transcript in the project dir. Two agents in the same cwd (or a subagent transcript) can shadow the session you're actually looking at — no pane↔session-file correlation exists.

worktree-per-task makes cwds unique (each gets its own slug); longer-term, correlate pane → session id.

medium Pane-detection assumptions

Everything keys on pane_current_command == "claude" and exact-cwd match — wrapped binaries or agents launched from a subdirectory are invisible to lib.sh and the picker.

tolerate prefix-match cwd; document the constraint (launch agents at repo root).

medium Docs drift

scripts/instructions.md predates the notification work: no claude-status.sh, notify hook, prefix+j/J, or pane-focus-in hook. nvim instructions.md still claims lib.sh "is not version-controlled" (it is, via stow). Headless tests live in /tmp, unversioned.

refresh both docs on this branch; move tests into the repo.

medium Content-scan version pin

pane_awaiting_input() greps for Claude Code v2.1.179 modal text. It was supposed to be deletable once hooks shipped — it can't be deleted because the hooks aren't wired (see critical).

wire hooks, run a week, then delete the scan (as the decision doc intended).

The end goal — flows we're catering for

Pragmatic framing: a task is the unit of work — typically a branch/worktree with an agent attached, some notes, and a trail of decisions. The tmux session is the workbench. Six flows, each graded honestly on what exists today.

F1Capture a note in < 5 seconds

the ask
From anywhere — mid-review, mid-conversation — jot a thought without losing focus.
today
notes.sh (daily notes, prefix+M) and /park (global ledger, one line, <10 s) both work well.
gap
Neither is task-scoped: a note about the task you're staring at lands in today's daily file or a global ledger, not in the task's own record. No keybind adds a note to "this window's task".

F2Jump between tasks instantly

the ask
Switching tasks should be one gesture, landing with full context (agent, editor, notes).
today
Jump by repo (prefix+m) or by agent urgency (prefix+j, prefix+a picker). pr-review-session proves window-per-unit works.
gap
No task-level target to jump to: tasks aren't named, listed, or bound to windows/worktrees by any convention. Cycle-on-repeat deferred.

F3Every task has an agent

the ask
Starting a task means an agent exists for it, in the right place, with the right context loaded.
today
:ClaudeNew splits an agent in-place; ce-worktree + the seeding rule (scratch/tasks → context) cover isolation; pr-review-session's driver does the whole ritual for PRs.
gap
No generic spin-up: "start task X" should mean worktree + window + agent + task file in one move. Today it's four manual steps. (Constraint from the stack audit: also needs a story for winding agents down.)

F4Task history is reviewable

the ask
Walk back into a task after days away and see prior discussion points and decisions at once.
today
decision-buffer leaves logs/decisions/*.md; transcripts are browsable per-message in nvim (:ClaudePick); scratch/tasks files capture intent.
gap
The trail is scattered across three stores keyed by repo/cwd/date — nothing assembles a per-task dossier. Transcript view is assistant-only and newest-session-wins, so older discussions are effectively unreachable.

F5At-a-glance board — done / planned / todo

the ask
One glance answers: what's finished, what's in flight, what's queued — across all tasks.
today
cad dashboard shows agent states (working/waiting/idle) — a liveness view, not a progress view. parked-items reviews deferred items weekly.
gap
Biggest missing piece. Task files have no machine-readable status convention (frontmatter), so nothing can aggregate them into a board. scratch/tasks/OVERVIEW.md is referenced by the worktree rule but doesn't exist.

F6Attention routing — agents pull you, you don't poll them

the ask
Know the moment an agent needs you; jump there in one key; signal clears itself.
today
Fully designed and built: hook → marker → ✳/✔ count → jump/preview → focus-clears. The best-thought-through part of the stack.
gap
Dormant — hooks not wired (see critical gap). Wiring it is step zero of everything else.

Design constraint from slice 7, honored from slice 2 onward: sessions are regenerative, not precious. A wb session must be fully derivable from its task record (repo, worktree, standard layout), so resume after a shutdown is "re-run wb new-equivalent from the store" — no fragile tmux state snapshotting. tmux-resurrect stays an optional complement for raw scrollback; the task store is the source of truth.
