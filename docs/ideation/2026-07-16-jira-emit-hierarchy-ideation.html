Jira emit flow · hierarchy sub-problem

Specifying a parent without forcing an Epic

A tight, single-question ideation (not the full fleet — the scope is one mechanism and the grounding is already in hand). Generate the ways to give created child tickets a parent, critique each on risk, and converge on the lowest-risk v1.

The question: when /wb-jira-create creates N child tickets from a wb task family, how do we let the user specify a parent the children hang under — with minimal risk, and not necessarily an Epic? (Your seed: a "parent task" field in the buffer, pick a parent for all children, just some linkage.)

▸ Grounding: the linkage landscape

Jira offers several ways to relate issues, and they differ sharply on config risk — the thing to minimize here:

MechanismConfig riskWhy
Generic issue links ("Relates", "Blocks"…)low Built-in system link types present in every Jira instance; independent of project type.
Epic + Epic Linkhigh The epic-link field differs by project style (team-managed parent vs company-managed Epic Link customfield). Unknown for SFB, and MCP is down so we can't probe it.
Native parent fieldmedium Works in team-managed; company-managed restricts what can parent what. Same risk class as epic-link.
Description mention (paste parent key in body)low-ish No link API, but whether a mention becomes a visible relationship depends on instance auto-link config — soft/unreliable.
The insight that shapes everything: generic issue links are the one mechanism that is config-independent and universally present. Any approach built on them dodges the epic-link uncertainty entirely — which is exactly the risk you flagged. SFB also has no Sub-task and no Story type, so native subtask hierarchy isn't even on the table here.

▸ The survivors

#7 — Polymorphic "parent ticket" field, linked generically recommended v1

Your seed, generalised and de-risked. The proposal buffer carries one optional field:

Parent ticket:  (blank = flat)  |  SFB-1234 (an existing ticket)  |  @1 (a row in this batch)

Whatever it resolves to, each created child gets a generic issue-link to that parent (default link type "Relates" — universal). Resolution rules:

  • An existing key/URL → link children to it (candidate 2). Good for "these belong under an existing Feature/Epic."
  • A batch row (default: the family's coordinator task, if there is one) → create that ticket first, capture its key, link the rest to it (candidate 3). Mirrors the family.
  • Blank → flat, no linkage (candidate 1). Graceful default.

+ Minimal risk — the only write beyond createJiraIssue is createIssueLink, which is config-independent. + Answers "specify a parent, not an Epic" exactly. + Human stays in control per-run in the buffer.
− "Relates" is symmetric, so Jira shows a link, not a true parent→child rollup (fidelity trade for safety).

One nuance worth a choice: "Relates" is non-directional. If you want a parent→child feel, some instances carry a directional type ("Blocks/Is blocked by", or a custom "Parent/Child"). Which types SFB actually has needs a single getIssueLinkTypes call — deferred until the MCP reconnects (it dropped mid-session). This is a low-risk verification, not a blocker: "Relates" is guaranteed present, so v1 works even if that's all there is.

Fallbacks, kept explicitly

  • #1 flat is the blank-field behaviour, not a separate feature.
  • #6 frontmatter-only is the retreat if createIssueLink itself proves unreliable in practice: record the chosen parent in the task file, link in Jira later.

Deferred to v2 (higher fidelity, higher config risk)

  • #4 fresh Epic + epic-link and #5 native parent field are the true-hierarchy upgrades. They become cheap and safe once we've confirmed SFB's project style and epic-link field (one probe when MCP is back). The polymorphic field from #7 is forward-compatible: the same "parent ticket" value can later drive an epic-link instead of a generic link, with no buffer change.

▸ Recommendation

Ship #7 as v1. A single optional "parent ticket" field in the proposal buffer, resolving to an existing ticket, a batch row (default: the family coordinator), or blank; children linked to it with a generic "Relates" issue-link. This is the lowest-risk mechanism that still lets you specify a parent, it needs zero knowledge of SFB's epic configuration, and it upgrades cleanly to real Epic hierarchy in v2 without reworking the buffer. The only follow-up is a one-call getIssueLinkTypes check (when MCP is back) to see whether a nicer directional link type than "Relates" exists.
