Family DAG view — how to build it

The what is settled (family-scoped dependency DAG; explicit size: → node scale; derived definedness → solid/dashed; hand-drawn inline-SVG node-link graph). This is the how: five ideation frames × five build-surface axes, critiqued by a fresh-context verifier. Two findings reshaped the ranking — the backbone is one small algorithm, and the feature's real risk is data, not rendering.

The headline risk is adoption — and on re-check it has split in two. At authoring the fear was one number: 1 of ~33 task files declared depends_on:. On the 2026-07-21 re-check the edges half has largely resolved itself: 10 of 59 files now populate depends_on:, and 9 of them form one genuine interlinked family — be--monorepo customer-download-files, a real fan-in/fan-out DAG (a foundations root, parallel events-gf/physical-gf branches, a unit-pass join). So the renderer would not draw an empty graph on day one — it has a real, non-trivial family to prove itself on immediately. But the sizes half is unchanged: size: still exists on 0 files, so node-scale and the CPM/ETA rollup (idea 4) remain speculative until idea 2's capture ships. Net: build the renderer against the real family now; still sequence the size: capture (idea 2) with — or before — anything that leans on duration.

1. A factored wb_board_deps_layer pass — the backbone LayoutConf 92%Cx Medium

DescriptionAdd one nameref function that mirrors the existing wb_board_deps_validate → _cycles → _blocking trio: a Kahn/longest-path walk over the already-validated, cycle-free DEPS_OF that emits LAYER[anchor] (topological depth) and CRITICAL_PATH[anchor], filtered to one family's node set. Keep the layout math (layer → x/y, edge control points) in a pure function, separate from a second function that emits the SVG string for @@TOKEN@@ substitution.
BasisdirectAll 5 frames converged here independently. wb_board_deps_cycles (wb.sh:3365) is an iterative BFS reachability walk (body 3368-3400) that answers "is there a cycle," never "what depth" — re-verified 2026-07-21: still no rank/layer/topo code anywhere in the file (the only wb_board_deps_* helpers are validate/cycles/blocking/chips). The three-function pipeline it slots beside is at wb.sh:4031-4034. externalKahn topological sort; Coffman–Graham / Sugiyama layer assignment (Graphviz dot rank model).
RationaleReframes "write a graph-layout engine in bash" (sounds infeasible) into "~30 lines mirroring a function that already ships." Every other visual promise — lanes, spine, frontier, node x/y — is downstream of a per-node layer number, so this is the true critical path of the build. Splitting math from emission (frame L6) lets the same coordinates later feed a plain-text/ASCII renderer.
DownsidesBespoke crossing-minimization is explicitly out of scope here (see idea 6 / rejections) — v1 accepts some edge crossing. Cycle handling must be decided first (idea 6). Folds in two hygiene notes: consume DEPS_OF as-is (no second depends_on: parser), and emit shared data-depth/data-crit attributes so lane placement and the sort script never drift.

2. Capture size: & depends_on: at breakdown time — and edit from the graph DataConf 85%Cx Medium

Descriptionwb breakdown --apply is the one moment a whole family is enumerated together in a locked, human-approved write. Extend its proposal buffer to capture each child's size: and its blocking relationships — and default each child to depend on its predecessor in the approved order, so declaring parallelism becomes the explicit exception rather than every edge being hand-typed. Downstream, since the board is static HTML, let each node emit a one-click copy-out wb dep add <child> <blocker> / wb size <child> L so the graph becomes a command palette for its own structure.
BasisdirectRe-verified 2026-07-21: 10 of 59 task files now carry a non-blank depends_on: (was 1/~33 at authoring) — but 0 carry size:, which still doesn't exist as a field. wb_seed_task blank-fills depends_on: for every task (wb.sh:620-623). Families are defined purely by parent: frontmatter written at creation (STEM_PARENT wb.sh:3904 → ANCHOR_FAMILY 3986-3987, commit 43d899f). reasonedBreakdown is the only moment the author holds the whole family's shape; capturing two fields there is near-zero marginal cost vs a retroactive backfill nobody does.
RationaleStill the make-or-break — but the burden has shifted from depends_on: to size:. Edges arrived organically (one real 9-node family already, see headline), so the renderer won't be empty on day one; size: however is at zero adoption, so node-scale and every duration-derived signal (idea 4) draw nothing until capture ships. Fixing both at breakdown time bootstraps every new family with real structure for free, and the predecessor-default edge convention means even authors who skip the deps UI still get a sensible chain.
DownsidesDoesn't retrofit the existing backlog (that's the deferred "inferred edges" fork — see rejections). Adds UX weight to the breakdown proposal buffer. Copy-out editing is a workaround for static HTML, not true in-place editing. Converges: P4 · I2 · L4 · A5 · R5.

3. The DAG rides the existing family filter / parent card — no new tab PlacementConf 88%Cx Low

DescriptionSettles the open placement question. Two compatible flavors: (a) render the inline-SVG as the body of the expanded parent <details class="parent-row"> card, replacing/augmenting the flat child list; and/or (b) selecting a family in the existing fp-* filter dropdown reveals a pre-rendered per-family SVG panel via the same #fp-$fam:checked ~ pattern the filter already uses.
BasisdirectThe family filter radios + hide CSS exist at wb.sh:4143-4164; rows already carry data-family tokens (built wb.sh:3986-3987, applied to card 3778 and rows 4209/4261/4328/4378); the parent card printf is at wb.sh:3867 (styled 4722-4731). Convergence across P7 · I4 · L3 · R1.
RationaleA standalone tab would duplicate the window/tab radio wiring and a family picker that already exists. Riding the filter means "where does the view live" dissolves — it's "more detail about a family already on screen," and filtering to one family gives the literal family view for free.
DownsidesLess first-load discoverability than a dedicated tab. Pre-rendering one SVG per family grows page weight (bounded by family count, which is small).

4. CPM: critical path + slack/float + a family ETA rollup SignalsConf 80%Cx Medium

DescriptionTreat size: as activity duration and apply the Critical Path Method on top of idea 1's layers: earliest-start = longest size-weighted path in, slack = latest-finish − earliest-start. Zero-slack nodes ARE the critical path (auto-derived, not a hand-picked spine), and positive-slack parallel tasks render with a "float" affordance. Sum the critical path's sizes for a family ETA and roll it into the existing children-rollup so the parent card, Pipeline tab, and future digests inherit it.
BasisexternalCritical Path Method (Kelley & Walker, 1959) / PERT — project duration = longest weighted path, not node count. directThe rollup loop to extend is verified at wb.sh:4046-4047 (consumed for the counter at 3862-3863); it computes CHILDREN_TOTAL/DONE today with no duration weighting.
RationaleThe most direct hit on "roughly how long" + "what can be done in parallel." An 8-child family with a 3-node critical path is short — node count would mislead. Turns the DAG from a picture into an estimate, and putting it in the rollup makes it a store-wide fact other surfaces reuse.
DownsidesETA credibility is only as good as size: adoption (gated on idea 2). Asserting an ETA means owning a wrong one. Converges: A3 · L2 · R4.

5. Frontier line + highlight all startable-now nodes SignalsConf 88%Cx Low

DescriptionThe "you are here" frontier is a pure rendering of data already in memory — no new schema. Go one step past a single marker: highlight every currently-startable node at once (UNMET_COUNT=0 and status not done/in-progress), answering "what can I do in parallel right now" literally instead of asking the reader to trace arrows.
Basisdirectwb_board_deps_blocking already computes per-anchor unmet/blocker + unblocks (wb.sh:3417), exposed as UNMET_COUNT/BLOCKER_NAMES/UNBLOCKS_* (decl wb.sh:3926-3929). Re-verified exact 2026-07-21.
RationaleDirectly answers the user's stated pain ("what next steps are") as a computed set, not a picture to interpret — and it's essentially free, riding the existing blocked/unblocks machinery with zero new frontmatter.
DownsidesHighlighting "all startable" is only meaningful once edges exist (gated on idea 2); on a zero-edge family everything is trivially startable. Converges: P8 · I5 · I8.

6. Always render something honest — cycles, dangling deps, and no-edge families LayoutConf 85%Cx Low/Med

DescriptionA layout engine has no defined behavior on a cyclic subgraph, so decide the fallback before writing the layering pass. Three coordinated moves: lay out the acyclic majority and draw offending edges as red git-style back-edges (with the existing CYCLE_WARN inline); when a graph can't be trusted at all, fall back to a monospace git log --graph ASCII lane diagram (structurally incapable of drawing a lie, and doubles as the narrow-viewport/print view); and give a genuinely edge-free family an explicit "no dependency data yet — add depends_on:" empty-state rather than a parallel column that masquerades as signal.
BasisdirectFailure modes are already detected and named — DANGLING_WARN/CYCLE_MEMBER/CYCLE_WARN at wb.sh:3923-3925, set by the fails-open cycle walk (_cycle_member nameref in wb_board_deps_cycles, wb.sh:3366) — they just have no visual today. externalgit log --graph ASCII DAG; Sugiyama tolerating a minimal feedback-arc set.
RationaleThe board's whole philosophy is "fail open, render something." A graph that blanks on one bad edge betrays that; reusing already-computed flags makes robustness nearly free. The empty-state is the honest answer to the adoption reality (idea 2's risk) — and a deliberate fork away from guessing edges (see rejections).
DownsidesAn ASCII fallback is a second renderer to maintain (mitigated by idea 1's math/emission split). Deciding "how many edges is enough to draw the SVG" is a threshold call. Converges: P2 · P3 · I7 · A8 · R6.

7. Interactivity: bank the JS budget (CSS :checked cones) — or spend it once InteractivityConf 70%Cx Low/Med

DescriptionThe no-JS relaxation is granted — so make it an explicit choice, not a drift. Recommended v1: stay zero-JS — emit a hidden radio + a <label> overlay per node and light its upstream/downstream cone with #node-x:checked ~ svg .downstream-of-x { opacity:1 }, the exact :checked ~ primitive the repo/family filters already run on. The precomputed cones are what idea 1's layering pass already knows. Escalation: one justified second <script> (following the sort-script precedent) for hover-driven highlighting if click-to-focus proves too coarse.
BasisdirectThe :checked ~ sibling-targeting primitive is proven across the tl/st/fr/fp filters, e.g. repo_hide_css (decl wb.sh:4128, selector 4135). Update 2026-07-21: there is no longer a single sanctioned script — #33 added a no-FOUC theme-toggle script (wb.sh:4578-4602, self-described as "a deliberate second copy") alongside the click-to-sort script (wb.sh:4807-4841). So the board already runs two deliberate scoped scripts, each with a "this is an explicit exception" comment.
RationaleThis fork is upstream of several rejected flourishes (hover tooltips, click-to-trace, scrub playhead) — deciding it settles them. Banking the budget preserves the board's pre-rendered, git diff-able, offline-perfect identity exactly when that identity is up for grabs.
DownsidesCSS cones mean one hidden radio + label per node (markup weight) and click-not-hover interaction. The "adding a script breaks the one-exception norm" argument is now weaker — the norm is already two exceptions (theme + sort) as of #33 — so an interactivity script would be incremental, not a philosophical first break. The stronger reason to bank is preserving the pre-rendered, offline-perfect, git diff-able identity, not exception-counting. Fork: R3 (bank) vs L5 (spend); see decision Dc.

§ Decisions to resolve before building

These are forks the ideation surfaced, not ideas — each shapes how idea 1 gets scoped. They're the natural input to a ce-brainstorm / ce-plan pass.

Da · What is a "family"? (challenges resolved D1)

Frame 5 reframed "family" as the dependency cone around the in-progress node (transitive DEPS_OF + UNBLOCKS) rather than a parent's children. It's a strict superset when deps stay in-family (which D1 says they do) but also handles parentless / cross-parent chains. This defines the exact node set idea 1's layering pass filters to, so it must be answered first.
Recommendation: keep D1 (parent's children) for v1, but write wb_board_deps_layer to take an arbitrary node set — then "cone" is a later filter swap, not a rewrite.

Db · No-edge families: honest empty-state vs inferred edges

Idea 6 shows an honest "no data yet" empty-state; the deferred alternative infers a faint provisional chain from creation order and asks you to confirm it.
Recommendation: honest empty-state for v1. Inferred edges risk being confidently wrong on exactly the un-annotated backlog they target, and would pollute the validated DEPS_OF pipeline unless explicitly tagged and excluded from cycle/blocked logic.

Dc · Spend the JS budget now, or bank it?

Idea 7's fork. Settling it also settles whether the rejected tooltip/click-trace/playhead flourishes are in scope. Note (2026-07-21): the board now ships two scoped scripts (#33's theme toggle + sort), so "adding a script breaks the one-exception rule" is no longer the deciding argument.
Recommendation: still bank it — ship zero-JS CSS cones in v1 — but on the durable grounds (pre-rendered, offline, git diff-able), not exception-counting. Revisit a scoped script only if click-to-focus proves too coarse.

Dd · Sequencing (re-checked: 10/59 depends_on:, 0 size:)

The adoption picture split since authoring: edges now exist on a real family, sizes don't exist at all.
Recommendation: build the renderer + idea 6's empty-state against the real customer-download-files family now (it's a genuine day-one test case), and ship idea 2's size: capture with or before any duration-derived surface (node-scale, CPM/ETA — idea 4), which otherwise draws nothing.
