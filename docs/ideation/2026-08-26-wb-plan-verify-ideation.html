Strengthening wb's brainstorm → plan → verification stages

Treating this as a topic in this codebase — about closing gaps in the wb workflow between a raw task and a confidently-implemented one: requirements interrogation, staged critical-path scoping, breakdown quality, plan verification, and implementation confidence.

Grounding used — this run reused two research passes already completed earlier in-session (skill-inventory audit of ~/.claude/skills/ + docs/roadmap.md; external survey of Spec Kit, Kiro spec-mode, Shape Up, Walking Skeleton, MoSCoW/RICE, INVEST, adversarial pre-mortem review, generate-then-critique loops, tiered DoD) instead of re-dispatching grounding agents, since that material was already gathered this session against the same topic.

Topic axes

1 · Requirements interrogationRaw ticket → tight, well-understood requirements, before any decomposition.
2 · Staged critical-path scopingBroad requirement set → MVP / Good / Fully-spec-complete tiers, with everything below the line explicitly deferred.
3 · Breakdown qualityThe moment wb breakdown actually splits a task — are the resulting children understood, not just sized.
4 · Plan verificationConfidence in a plan before code is written.
5 · Implementation confidenceConfidence that what got built actually matches intent, after the fact.

Survivors (5)

#1 /spec-interrogate

axis 1new skillupstream of wb-breakdown

Directly answers pain point 3. Takes a raw task/ticket, runs one targeted interrogation pass (single-select where possible, per the ce-ideate interaction convention), and emits a requirements doc scored against INVEST (Independent/Negotiable/Valuable/Estimable/Small/Testable) as the exit gate — mirroring Spec Kit's /specify phase and Kiro's EARS-formatted requirements, the two clearest existing implementations of this exact step.

Pro
  • Solves the root cause of pain point 1 (breakdown-before-understanding) rather than patching breakdown itself
  • Reuses proven prior art (INVEST, EARS) instead of inventing a novel rubric
  • Composable — its output doc becomes the input to /critical-path and wb-breakdown
Con
  • Adds a step to every task's front — real friction cost if not kept fast for small tasks
  • Needs a "trivial task, skip this" escape hatch or it will get bypassed like any unenforced ceremony

Basis: internal pain point 3 (session brief) + external Spec Kit/Kiro spec-mode, INVEST criteria (prior research, this session).

#2 /critical-path

axis 2new skillnamed explicitly by user

Takes a requirements doc (ideally /spec-interrogate's output) and stages it into MVP → Good → Fully-spec-complete, using Shape Up's appetite + no-gos framing: MVP is the walking skeleton that ships, Good and Full-spec items are explicitly named and deferred rather than silently dropped. This is the most directly-requested item in the brief and has the cleanest ready-made scaffold of anything surveyed.

Pro
  • Exact match to a named ask, not an inferred one
  • Shape Up's "no-gos" list gives a concrete artifact shape (not just prose) — a checklist the user can react to like a decision-buffer
  • Naturally feeds wb-breakdown a pre-scoped MVP tier to split first
Con
  • Staging judgment (what's "Good" vs "Full") is subjective — needs the human to confirm tiers, not just accept an LLM's split
  • Risk of becoming yet another buffer doc the user has to read through if not kept tight

Basis: internal pain point 2, verbatim from the user's brief. external Shape Up appetite/no-gos, Walking Skeleton/Steel Thread (prior research, this session).

#3 /plan-premortem

axis 4new skillverification

An adversarial plan-review pass — 2-3 independent skeptic reads of a plan or task file, each prompted to argue it fails, before implementation starts. Directly ports the plan-review-adversarial community pattern and the generate-then-critique self-critique research finding into a wb-integrated step.

Pro
  • Cheapest of the survivors to build — it's a review pass over an existing artifact, no new document format
  • Directly answers pain point 4 (confidence before building)
  • Composes naturally as a gate right before wb resume/first commit on a task
Con
  • Only as good as the plan it's reviewing — garbage-in if run before /spec-interrogate//critical-path exist
  • Risk of alert fatigue if it fires on every task regardless of size

Basis: external Smithery plan-review-adversarial skill, arXiv 2512.24103 generate-then-critique (prior research, this session).

#4 wb-breakdown: walking-skeleton note per child

axis 3modify existing skillsmall

The smallest, cheapest change on this list: when wb-breakdown generates child tasks, require one sentence per child stating the thin, testable slice it proves — not just a title and a size estimate. Directly targets "the pieces stay vague until someone implements them" by forcing the breakdown step itself to state what "done" looks like for each piece, before anyone picks it up.

Pro
  • Incremental — a prompt-template change to an existing, already-adopted skill, not a new skill to learn
  • Directly targets the exact symptom described in the brief
Con
  • Treats the symptom (vague children) rather than the cause (breakdown running before interrogation) — should be paired with #1, not a substitute for it

Basis: internal pain point 1 (session brief) + Walking Skeleton pattern (prior research).

#5 /verify-against-spec

axis 5new skillpost-implementation

A closing-the-loop skill: diffs what actually got built against the tiered requirements doc from /spec-interrogate + /critical-path, flagging both unmet MUST items and unrequested scope creep, run before wb done/close-out. This is the "confidence after building" half of pain point 4 that /plan-premortem doesn't cover.

Pro
  • Closes the loop the other four ideas open — without it, the tiered spec is only ever aspirational
  • Natural composition point: slots into close-out, which already sweeps a session before wb done
Con
  • Fully dependent on #1/#2 existing and being used — low value in isolation
  • "Diff intent vs implementation" is a harder LLM task than the others here; likely to need iteration to get signal-to-noise right

Basis: internal pain point 4, second half (session brief) + tiered Definition-of-Done pattern (prior research).

Rejected — why (grouped, not repeated per-row)

  • Mega-skill combining interrogation + critical-path + breakdown (#7): violates the existing dotfiles convention of small, composable skills (wb-save/wb-resume/wb-done are already split this way) — a monolith is harder to invoke partially and harder to iterate on.
  • Hard gates (#2, #10): forcing interrogation/premortem to block breakdown risks the same fate the audit flagged for ceremony-heavy steps — unenforced-by-tooling rules get skipped under time pressure. Better as a strongly-defaulted-on step with an explicit skip, not a hard block.
  • Folding into existing skills (#8, #13, #16): decision-buffer, ce-plan, and ce-code-review already have clear, narrower jobs; bolting new phases onto them dilutes what each is for and duplicates the plugin-vs-dotfiles overlap already flagged in the earlier audit.
  • Enforcement via hooks/scoring (#4, #6): mechanical INVEST/RICE scoring without human judgment produces theater, not confidence — these frameworks are meant as discussion aids, not gates a script enforces.
  • Generic red-team command with no task-store integration (#14): loses all the value of being wb-aware (which task, which requirements doc to check against).

Round 3 — pipeline expansion from human feedback

Feedback that triggered this round: (1) testable-acceptance-criteria deserves its own skill, not just a field on /spec-interrogate's output; (2) a fuller pipeline shape — idea → (maybe ideate) → spec-interrogate → acceptance-criteria → prd → critical-path → breakdown — with the acceptance-criteria/PRD order and the critical-path/breakdown order both flagged as uncertain; (3) want an any-time "am I still on track to the big picture" check runnable from inside a child task; (4) want a roadmap visualization skill.

Resolving the two ordering questions

Acceptance-criteria vs PRD — PRD goes first. A PRD is the stakeholder-facing "what and why" — the thing you'd actually show someone to confirm you're building the right thing. Acceptance criteria are testable derivations of what the PRD commits to. Writing criteria before the PRD exists means locking in tests against requirements that haven't been confirmed yet — if the PRD review changes scope, you've thrown away test work. This also matches how /spec-interrogate already behaves: it resolves ambiguity and produces a tight requirements doc, which is functionally a lightweight PRD. So the resolved order treats interrogation's output as the PRD input, with a distinct polishing/PRD-formatting step only where a repo genuinely needs a stakeholder-facing document (see #6 below on whether that's a separate skill or a mode).

Critical-path vs breakdown — critical-path stays first, with a caveat. Critical-path's entire job is deciding which pieces are MVP vs deferred; breakdown's job is splitting the chosen pieces into session-sized tasks. Running breakdown first would mean splitting work before knowing what's in scope — defeats the purpose. The real tension you may be sensing is estimation: you often don't know true effort/complexity until you've broken something down. The resolution most teams land on (and the one that fits your composable-skill convention) is a rough pass, not a full breakdown, informing critical-path's staging — wb-breakdown itself already produces session-sized, estimable children, so critical-path can lean on a lightweight version of that same splitting logic for sizing without doing the full production breakdown twice.

#6 /spec-acceptance-criteria

new skillsplit from round 2's #1

Your instinct was right, and it's consistent with a principle this session already established twice (round 1's rejection of a mega-skill, and wb's existing small-composable convention: wb-save/wb-resume/wb-done are already split this granularly). Splitting it out also cleanly separates two different failure modes: /spec-interrogate can be wrong about what is required; /spec-acceptance-criteria can be wrong about how to test a requirement that's correctly stated. Conflating them in one skill made both harder to debug independently.

Pro
  • Matches the established composable-skill convention rather than fighting it
  • Lets /critical-path stay a pure staging/tiering skill — it consumes tests, doesn't generate them, which was a round-2 con (test-generation quality was "load-bearing" for a skill whose real job is prioritization)
Con
  • One more skill in the chain — real risk of ceremony fatigue on small tasks unless each step stays fast and has a "trivial task, skip" escape hatch (same caveat as round 1's #1)

Basis: internal user feedback this round, verbatim. Supersedes round 2's "criteria as a field" design.

#7 /on-track

new skillmid-flight, not end-of-task

Fills a real gap none of the prior rounds covered: everything so far checks alignment either before implementation (/plan-premortem → the doc-review skeptic lens) or at the very end (close-out's tier-test check). Nothing lets you check mid-flight, from inside a child task you've been heads-down in for a while, whether you've drifted from what the parent's critical-path actually scoped you for. This is the single biggest omission across rounds 1-2.

Pro
  • Closes a real gap — mid-flight drift-checking has no analog anywhere else in the pipeline
  • Cheap to build: read the parent's critical-path doc + this child's scope, compare, report — no new document format
  • Natural fit for the existing wb parent/child linkage wb-breakdown already establishes
Con
  • Only as useful as the parent's critical-path doc is current — if scope changed upstream and nobody updated the doc, this reports false confidence

Basis: internal user feedback this round, verbatim — a genuinely new axis, not a revision of a prior survivor.
