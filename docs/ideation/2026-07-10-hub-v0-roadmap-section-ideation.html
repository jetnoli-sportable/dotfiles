R1

One status grammar — stage × impediment — ratified across all four surfaces

state-taxonomy Confidence 80% Complexity: Medium
Description
The ~15 prose status strings in the Overview table are not 15 states — they are combinations of two orthogonal dimensions: a commitment stage (a small fixed vocabulary, e.g. shipped / shakedown / active / queued / proposed / parked) and an impediment clause (free prose: "waiting on X", "pending the ~07-14 verdict", empty for most rows). "Blocked" and "at risk" were never stages — they are impediments, and forcing them into the category set is what makes the taxonomy question feel unresolvable. Write each row as stage-word + free prose, and ratify the same stage names across the task-store enum, /board's tabs (cashing the reserved empty pending/Deferred slot at wb.sh:1183), the roadmap table, and the visual's zones. The shakedown stage (shipped but not yet proven in use — aviation "return to service") names a state three rows already occupy with no word for it: 4a shipped pending its ~07-14 verdict, wb reconcile done-with-a-named-gap, PR #14's "verify yourself" recap.
Basis
direct: the state-taxonomy dossier catalogues ~15 distinct status strings from docs/roadmap.md:42–67 against the task store's 5-value enum; docs/roadmap.md:63 — "Open, actually blocked on the personal/employer boundary rule below, despite reading as unblocked" — a row that needs bold italics to fight its own status word; wb.sh:1183 reserves the board's Deferred tab "for a future pending status". external: TC39 stages 0–4 (commitment by stage, entrance/exit criteria, no dates); METAR's controlled-vocabulary head + free-remarks tail.
Rationale
This answers the open taxonomy thread decisively: done/active/follow-up/deferred aren't wrong, they're one axis of two. It is also the single highest-leverage move in the set — one decision retires the empty board tab, defines the visual's zones, makes the table scannable in one pass, and pre-answers the parked "task-store schema migration" row (docs/roadmap.md:65) that is currently waiting for the schema to "settle". The verifier ranked the cross-surface unification the strongest single ingredient of all 48 candidates.
Downsides
Touching the Status column's wording brushes against R11 ("the Overview table's rendered content is unchanged") — adopting R1 in-PR means amending that requirement or scheduling the reword as the schema-migration follow-up. The vocabulary itself is a real editorial decision (six-ish words that have to hold up for a while).

Illustrative: each prose status decomposes losslessly into a fixed stage word plus a free impediment clause; the stage set is then shared by all four surfaces instead of four vocabularies drifting independently.

R2

"Blocked" always names its blocker — a written waits-on link, never a bare word

dependency-vs-sequencing Confidence 85% Complexity: Low
Description
Today a row says it is blocked with a word inside a sentence — "Open, actually blocked on…" — a description the reader has to notice and interpret. The proposal: the bare word gets banned. Any row that is waiting must write a small, recognizable notation naming what it waits on: needs: boundary-rule when the blocker is another item, clock: 4a verdict ~07-14 when it's a dated check-in, and a chosen ordering written honestly as a choice — after: Hub v0 — chosen, PR scoping. Each of those is a written link between two named items (an "edge", in graph terms — that's all the word means). The payoff: the dependency-depth view's entire content turned out to be about five such links plus one finding — so the four-column view is not kept as a maintained page section at all. It is rebuilt from the per-row links on demand, as a dated, archived audit (a "resurvey", like a nautical chart edition) — the mockups-v2 file in logs/decisions/ is de facto edition #1. This answers the "is the dependency view worth building for real?" thread with the third option nobody had tabled: keep the data (one line on ~5 rows), rebuild the view on cadence, retire the maintained matrix.
Basis
direct: logs/decisions/2026-07-10-roadmap-visual-mockups-v2.html:298 — "Sequenced right after Hub v0 by choice (kept the Hub v0 PR from growing), not because it technically depends on Hub v0 — nothing stops it starting in parallel" — while docs/roadmap.md:55 carries no "by choice" qualifier; the view's columns hold 7/3/1/1 items (verified), i.e. ~5 real waits-on links; the same node ("Unify copy/paste") sits in two different hand-placed positions across the mockup's two views (:215 vs :246). external: Rothman (2024) — dependency graphs rot as maintained artifacts; per-item "blocked by X" narrative scales for a single maintainer.
Rationale
The bare word rots silently — "blocked" stays in the prose after the blocker ships. A named link audits itself: the day boundary-rule flips to done, every row still saying needs: boundary-rule is visibly stale. The real-blocker-vs-chosen-order distinction the mockup exercise discovered becomes impossible to blur by accident, and every future consumer (generated roadmap, /board roadmap view) inherits it for free. The maintained-matrix alternative doubles the "sync by habit" surface D4/D13 already accepted for one artifact.
Downsides
The needs:/after:/clock: notation is one more authoring convention to remember (mitigated: it applies to ~5 rows today). The resurvey only stays honest if it actually recurs — which is what R5 exists to guarantee.

Illustrative: the maintained four-column matrix is replaced by ~5 one-line waits-on links on the rows; the view is rebuilt and archived on cadence instead of hand-synced forever.

R3

Resolve the node-interactivity contradiction; make the anchors permanent slugs

data-source-maintenance Confidence 95% Complexity: Low
Description
The written U7 plan and the mockup direction you like cannot both ship: the plan specifies non-interactive steps, the mockup makes every node a real anchor link to a detail entry. Resolve it deliberately, before merge — and resolve it toward anchors: each node's #detail-<slug> id becomes the item's permanent slug, the join key a future generated roadmap, task-store id:, or /board cross-link will need. Deciding the naming convention now, while it's just an HTML anchor nobody parses, costs nothing; inventing it retroactively means a slug-migration pass across every row.
Basis
direct: docs/plans/2026-07-10-001-feat-hub-v0-meta-documentation-plan.md:497–501 — "Steps are non-interactive (no click-through to the table row, no legend)" — versus logs/decisions/2026-07-10-roadmap-visual-mockups-v2.html:203–207, where every node is a literal <a href="#detail-…">. Verified by the fresh-context pass: "sound, effectively mandatory." The generation trigger is already named at logs/decisions/2026-07-09-hub-v0-scoping.md:34–39.
Rationale
This is the one survivor that isn't optional: whichever way it's resolved, the plan as written currently ships something different from the direction marked as liked. The slug half is the cheapest structure-now-for-generation-later move in the whole candidate set.
Downsides
Essentially none for the decision itself; choosing anchors adds a small amount of markup per node and commits to slug stability (renames become deliberate acts).

R4

Shrink the live surface: Done rows leave for the recap ledger, proposals move to an un-promised pool

page-architecture Confidence 75% Complexity: Medium
Description
11 of the 24 Overview rows are Done, and 8 of those already link to a recap page that is the real durable record — one Done row (roadmap.md:67) is a bugfix that was never a roadmap item at all, it accreted because no other shipped-ledger exists. Move Done rows off the page entirely (the "12 shipped" chip links to the recap spine), and move the three bare "Proposal, unratified/unscheduled" rows into an explicitly un-promised parked pool where no entry may be parked without naming its revisit trigger — a date or an event (roadmap.md:61 already writes one, ":66" has none). A row graduates back the moment work starts, which is also when it gets a task file — stating that currently-implicit rule on the page. What remains is a live table of ~10 rows that are actually moving. This deliberately reopens R11 ("the Overview table's rendered content — including Done rows — is unchanged"): adopt it as a conscious amendment, not a quiet tweak.
Basis
direct: exact counts verified — 11/24 Done rows, 3 proposal rows (docs/roadmap.md:61,62,66), 6 rows with "—" in the Doc column; roadmap.md:61 — "Only revisit if artifacts still go missing after the landing-path rule" (an expiry condition with no mechanism). external: Shape Up "Bets, Not Backlogs" (backlogs rot; the important resurfaces); GTD someday-maybe (un-promised lanes are cheap); Sivers /now (the page is a tool for the present, not an archive). direct: (added same day) the user-journeys review's J4 — wb board, todo.md, and the roadmap table "all answer some version of 'what's going on'… nothing today tells you to check one over another" — the cross-surface form of this idea's diagnosis, raising confidence from 65%.
Rationale
The calibration thread's core complaint — "what's actually in place vs only ever planned" — is half-caused by 46% of the table being inert history competing for attention with live work. The compact-path mockup already collapses shipped items in the visual; this makes the table agree instead of the two surfaces disagreeing about what the roadmap is for.
Downsides
Reopens a settled requirement (R11) — the verifier flagged that all Done-eviction candidates presented as tweaks when they are really a reopen proposal; this card says so explicitly. Losing the single-page "everything ever" view has real value too — mitigated by Hub v0's own artifact index and tab-2 "All docs" view, plus the recap ledger.

Illustrative: the one overloaded table splits by question — what happened (ledger), what's moving (live table), what's possible but un-promised (pool with mandatory revisit triggers).

R5

calibration-ritual Confidence 80% Complexity: Low
Description
Today's session is a calibration pass; the survivors above only stay true if calibration recurs by design, not luck. Hub v0 is already building docs/ceremonies.md (U3) "with room for future recurring reviews" — give it the roadmap's own instruments: (a) a recurring roadmap-accuracy resurvey as the fourth ceremony (rebuild the dependency view from R2's waits-on links, re-check every stage word, diff against the last edition, archive the dated snapshot — its rendered output doubles as a "changed since last check-in" delta strip); (b) a cold-agent briefing test as Hub v0's acceptance criterion — a fresh agent session, given only the rendered pages, must correctly answer what's built, what's blocked and on what, what's next, and what's deliberately un-promised; its wrong answers locate the unclear prose exactly; (c) the three dated clocks wired to real nudges (cron/schedule entries, plus surfacing roadmap.md's inert updated: field through the existing wb done nudge channel); (d) later, mechanized drift checks as a new wb reconcile finding type ("roadmap row disagrees with git-observed state" — the merged-status check already exists).
Basis
direct: the 2026-07-07 seven-persona review surfaced 12 findings and caught the stale-sequencing failure class twice (logs/decisions/2026-07-07-roadmap-review-findings.md:149–210) with no recurrence attached — and today's mockup exercise independently re-discovered the same class; review-findings.md:14–15 — findings were "independently verified against the actual repo" (the cold-reader precedent); docs/guides/parked-items.md:49–51 — the wb done nudge channel already exists; docs/roadmap-wb-reconcile.md:36–38 — the GitHub merged-status check already runs. external: solo-founder review cadence (~90-day half-life, Wayline); docs-as-code visible-staleness practice.

R6

The commitment queue: chosen order as one editorial object, capped

dependency-vs-sequencing Confidence 60% Complexity: Low
Description
Sequencing-by-choice is a single global decision you make, yet it's currently stored per-item, smeared across status prose ("Queued, marked for pickup soon", "Sequenced after /handoff…"). Represent it once: an explicit ordered pick-list of at most ~3 slots at the top of the page — "the order I currently intend" — while items themselves carry only true blockers (R2's waits-on links). Re-planning becomes reordering one short list instead of rewording N statuses, and the real-dependency/chosen-order distinction becomes structural: the queue is the chosen order, the links are the real dependencies.
Basis
direct: only 2 rows today carry the literal phrase "ready to implement" (docs/roadmap.md:54–55) — the genuine Now band is naturally 2–3 items; mockups-v2.html:298's "by choice… nothing stops it starting in parallel". external: Now/Next/Later — the commitment gradient is a property of the horizon bands, not of items; only "Now" carries delivery expectation, capped at 3–5 (ProdPad); Shape Up's small-batch betting.
Rationale
Forces the one genuinely hard editorial call — which ~3 items get the promise — that the current 15-string vocabulary lets the page avoid. Composes directly with R2 (waits-on links) and R4 (the pool): queue = chosen order, links = real constraints, pool = everything un-promised.
Downsides
More opinionated than the others — it changes how the top of the page is written and edited, and a hard cap occasionally fights reality (a genuine 4-item burst). Medium confidence because it's a workflow-style bet, not a drift fix.
