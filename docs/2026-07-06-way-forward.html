0Readback — the shape you described

  • Session per worktree (not per repo), standard layout: one window each for nvim, agent, and running things. Grouped so a repo's sessions are easy to see together.
  • One picker to rule them all: sessions and agents merged into a single view, since they're ~1:1. This replaces the s + ca split. cad retires.
  • Notes with a lifecycle: a notes surface per session/worktree, seeded on create, reviewed on close with keepers flowing into a central system; plus quick capture into long-living topic ledgers, periodically reviewed, with future automation proposing quick wins that you just green-light.
  • Record layer stays plain files serving three goals: per-task backlog / follow-ups, progress across all tasks + planned batches, easy review and refinement.
  • Keep untouched: worktree flow, /park + /parked-items (fix the channel bug), pr-review-session, decision-buffer. Keep the nvim bridge to its basic loop (output buffer + reply); fancy features on hold.

2The core — wb (workbench): session-per-worktree + the unified picker

One script in the existing lib.sh style, three verbs:

wb new <slug>          # from inside a repo (or wb new <repo> <slug>)
  → git worktree add .worktrees/<slug>; bootstrap via a per-repo gitignored
    .worktree-bootstrap manifest (paths to copy/symlink), default .env* when absent
  → seed the task file in the CENTRAL store if none exists
  → tmux session named for display only: sanitized "<repo>--<slug>" (/ and .
    become -); ground truth lives in session options @wb_repo + @wb_slug + @task
  → win1 nvim · win2 agent (LAZY: window exists, claude starts on first visit
    or wb new --agent — bounded by the ~10-concurrent-agent memory ceiling)
  → win3 shell

wb                     # THE picker (replaces s and ca muscle memory)
  → ROW SOURCE (decided 2026-07-06): one row per TASK from the central store,
    live session/agent state overlaid as glyphs. Repo-level checkouts appear
    as extra rows. Enter on a session-less task row runs the wb new spin-up.
  → grouped by repo; urgency (needs-you / finished) pins to the top of its
    group, mirroring ca's rank order. Changed 2026-07-06, post-launch:
    grouping is now status-first, not repo-first — needs-you rows surface
    together across every repo, then finished, working, idle. A session's
    sub-rows still ride along with their parent as one block.
  → sessions with >1 claude pane expand to one indented sub-row per agent.
  → ctrl-x on a worktree-backed task row routes through the wb done flow.
  → status line shows the pending Follow-ups + parked count.

wb done [<slug>]       # the wind-down that doesn't exist today — SAFE ORDER:
  1. fail fast: git status --porcelain in the worktree; abort if dirty
  2. open task file + session notes in a review buffer, keepers marked `- [x] keep`
  3. on close: sweep worktree-local gitignored keepers into the central store
  4. status → done, keepers captured
  5. kill session, then git worktree remove

Repo-level sessions (dotfiles, main checkout) remain plain rows in the same picker — s's job is absorbed, and the worktree-invisibility bug dies with it. Keybind: cutover — prefix+m and prefix+a both rebind to wb the moment it lands; s/ca stay invocable by name as fallback.

your take

answer · 2026-07-06

Bash for v1. wb is tmux/fzf orchestration — bash is the native tongue there, lib.sh already has the helpers, no build step, and it stows like everything else. A compiled implementation earns its keep only if the task index grows real querying/aggregation needs — and that's notes-tui / cli-kit territory (Go), not a reason to start wb in Go. 3The record — task files that can back a board

---
status: doing        # planned | doing | review | done
repo: dotfiles        # worktree resolves as ~/code/<repo>/<worktree>
branch: feat/agent-task-workflow
worktree: .worktrees/feat/agent-task-workflow
tags: []              # free tags for cross-project grouping
created: 2026-07-06
---
# Agent task workflow
## Plan          ← batches of intended work
## Done          ← running log of what landed
## Follow-ups    ← per-task backlog; /parked-items review reads these
## Decisions     ← links to logs/decisions/*.md + key calls inline

The three goals map: backlog = ## Follow-ups (+ global /park for cross-task strays); progress tracker = status: rendered in the picker — the board is inside wb, not a separate surface; review & refinement = wb done's close-out buffer plus a push trigger: the picker status line carries the pending Follow-ups + parked count and wb done offers the cross-task sweep past a threshold — the weekly /parked-items ritual stays available but is no longer the load-bearing path.

Topic ledgers = tags in its Denote scheme rather than a parallel system. notes.sh daily flow keeps working untouched on the same corpus.

addition · 2026-07-06, post-ratification

Every .md/.html pair built so far (this doc, the dotfiles overview) was hand-authored twice — write the markdown, then manually keep an HTML render in sync alongside it. That's exactly the kind of drift this section exists to prevent. Look at a proper doc-sync tool: one markdown file in a specific, defined format (frontmatter + section conventions), and a small generator that renders the HTML from it — single source of truth, regenerate on demand instead of hand-editing two files in parallel. Scope this alongside slice 5 (same "generated, not hand-maintained" principle as the help dashboard's index); exact format/generator choice goes through a quick decision buffer when it's built. not started — slice 5

9b. Day bookends — startup/shutdown flows
