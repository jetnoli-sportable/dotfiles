# validate-review-comments learnings

One dated line per entry: what surprised on a run (a mapping the script got
wrong, a misread comment, a page Jet found unhelpful), the target, and the run
directory. Sportable runs log in their own dossier instead, and only a
scrubbed, skill-changing lesson comes here. See `SKILL.md`'s Learnings ledger
section.

- 2026-10-22 — API shape, captured on a synthetic pending review on a dotfiles PR before the script was written: pending review comments carry no `line`, `original_line`, `side`, `start_line`, `start_side` or `subject_type` keys at all (not null, absent), only `position`, `original_position`, `diff_hunk` and `commit_id`. Every `diff_hunk` ended on the commented line, a deleted-line comment's hunk ending in its `-` line; a multi-line comment comes back as its end line only, its start line lost.
- 2026-10-23 — dry run, dotfiles PR #103 (synthetic pending review, 5 line comments + 1 file-level), run dir `dossiers/dotfiles--skill-validate-review-comments/validate-comments/pr103/`. One session, no subagents; most of the time went on judging (reading callers and tests), not mapping. The PR was rebased after drafting, which gave real moved/gone cases for free: GitHub re-pointed four comments' `commit_id` to the new head but kept their old `diff_hunk`, and left the one whose line was rewritten on the old commit; the script's text search found the three moved lines and called the rewritten one `gone`, all correct. A file-level comment comes back with `diff_hunk: ""`, `position: 1` and no `subject_type`. Re-run after editing one comment flagged only that one. Fixed in the skill: a `gone` record had no excerpt, so the card had nothing to quote (now the hunk as drafted); full paths in card headings made the nav unreadable (now the file name). For the dry run's own setup: REST can't edit a pending comment (PATCH `/pulls/comments/<id>` gives 404), GraphQL `updatePullRequestReviewComment` with the node id can; a file-level pending comment needs GraphQL `addPullRequestReviewThread`.
